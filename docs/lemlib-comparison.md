# Why this design goes beyond LemLib 0.5.6

This comparison is scoped to the 0.5.6 binary and headers used by 4613R, not to
unreleased LemLib work. LemLib remains a useful, approachable PROS library.

| Concern | LemLib 0.5.6 | VantagePath |
|---|---|---|
| Path reference | geometric pure pursuit with one caller-selected lookahead | timed pose, curvature, velocity, and acceleration |
| Complex turns | trades accuracy against speed through fixed lookahead | slows in advance from curvature, wheel-speed, and acceleration limits |
| Arrival | geometric motion plus timeout/exit conditions | planned zero end speed plus pose/heading/wheel settle window |
| Plant model | motor command generated by lateral/angular motion PID | per-side characterized voltage feedforward and wheel velocity feedback |
| Saturation | command-level limiting | battery-aware paired voltage scaling preserves curvature |
| Integrator | generic PID behavior | bounded conditional integration and filtered derivative-on-measurement |
| Failure reporting | motion completion/timeout APIs | distinct settled, timeout, divergence, saturation, and cancel signals |
| Portability | coupled to PROS/V5 chassis abstractions | hardware-agnostic C++17 core with a thin adapter |
| Testability | robot-oriented library binary in this project | native CMake tests for geometry, constraints, control, and odometry |

## Observed limitations in the 4613R integration

- The repository carries LemLib as a prebuilt archive, so its implementation is
  not inspectable or patchable in the project and the target ABI must match.
- The current lateral gains began as template values; angular was tuned later,
  while physical track width and drift remain incompletely characterized.
- Forward localization currently falls back to mixed-cartridge drive encoders;
  no tracking pods are connected and only one of the planned two IMUs exists.
- `moveToPose` is a boomerang/carrot controller; LemLib's own documentation says
  it is slower than `moveToPoint`, and a maintainer notes it is poor for short
  motions or large heading changes.
- Pure pursuit exposes a fixed lookahead. Its documentation explicitly frames
  smaller lookahead as closer/slower and larger as looser/faster; a request for
  velocity-dependent lookahead was closed as not planned.
- A path asset encodes geometry/speed information generated by an external GUI,
  but the runtime API does not expose an end-to-end wheel-voltage model or
  per-wheel tracking telemetry.

## What “better” means here

VantagePath is better for this team's stated need—fast, complex, repeatable
tank-drive trajectories—because feasibility is handled before execution and
feedback tracks a dynamic state rather than a moving point. That does not make
it magically tuned. LemLib has far more field usage; VantagePath must complete
the hardware validation checklist before match deployment.
